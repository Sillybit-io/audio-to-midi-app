## Prompt

> Codify this repo's conventions into AGENTS.md. There is no AGENTS.md yet, so generate one from what is actually here.

## Without skill

An agent with no codification discipline still produces a readable file. It skims the tree, correctly recognises a skills catalogue with a Bun validator behind it, and writes rules that sound right for such a repository. The prose below is competent and most of the individual statements are defensible in the abstract. What the file is not is evidence: not one line points at a place in this repository, so a reader cannot check a single claim — and neither could the agent that wrote it.

````markdown
# AGENTS.md

## Project overview

silly-skills is a catalogue of AI skills. Each skill lives in `skills/<category>/<name>/SKILL.md`. A Bun script validates the catalogue.

## Coding conventions

- Use consistent naming across the repository. Skill names and directory names should be lowercase and hyphenated.
- Write clear, descriptive frontmatter for every skill so agents can find it.
- Keep documentation up to date as the code changes.
- Prefer small, focused functions with descriptive names.
- Use TypeScript's type system fully and avoid `any`.
- Add tests for new functionality.
- Follow Conventional Commits for commit messages.
- Format shell examples in fenced code blocks tagged `bash`.
- Keep line lengths reasonable and prose concise.

## Testing

Run `bun test` before committing. Run `bun run validate` to check the catalogue.
````

Measured against what this repository actually does, that draft fails in six ways:

- Not one rule carries a citation. The bar is two `path:line` references per rule, drawn from two different files, and nothing here clears it.
- "Prefer small, focused functions", "avoid `any`", and "keep line lengths reasonable" are imported best practice. No file was opened to produce them. The last one contradicts the repository's own configuration: `.markdownlint.jsonc` sets `"MD013": false`, so long lines are a deliberate choice here, not an oversight.
- "Add tests for new functionality" is aspirational. The repository holds exactly one test file, `scripts/validate.test.ts`, so the observed behaviour is the opposite of the stated rule. A future agent reads this as a standing instruction and writes tests nobody asked for, in a layout nothing here establishes.
- "tagged `bash`" silently picks a side of a split. `README.md` tags six shell fences `bash`; two skill files tag fourteen `sh`. The draft names the side with fewer files and fewer occurrences, mentions no disagreement, and hands the next agent a documented reason to rewrite fourteen working fences.
- The patterns every one of the nine skills follows — the `Use <skill-name> when you:` stem, the `MUST:` and `NEVER:` pair, the QA-checklist lead-in sentence, the four-backtick skeleton fence, the lint comment above the footer — are absent. The rules that would actually keep an agent's output indistinguishable from the existing catalogue are the ones missing.
- Nothing marks which bytes are generated. The next run either duplicates the file or overwrites whatever a human added in the meantime.

Three differences matter more than the rest. The contradiction is reported rather than settled: with both counts in front of them the team can pick `sh` or `bash` in a minute, whereas a rule that picked for them would have sent the next agent to rewrite the losing side with a documented mandate. The banner-comment candidate is dropped despite six occurrences, because all six sit in one file — the two-citation bar asks for two files that agree, and frequency inside a single file cannot substitute for that. And "Add tests for new functionality", the rule in the unguided draft a reader would most likely trust, never appears at all, because one test file is not a pattern and nothing in this repository states the rule.
